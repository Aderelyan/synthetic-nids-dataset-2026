## 5. Rekomendasi Penelitian

1. **Checklist validasi Fase 6 di v2 §4.5 hanya mencakup Windows phase.** Buat versi paralel untuk Linux phase (isolasi client-1/2/attacker↔internet, resolusi DNS `*.lab.local`, sinkronisasi waktu UTC) sebelum eksekusi skenario S-01/02/03/04/08/09/11/12 — tanpa ini, klaim "isolated lab" pada dataset tidak dapat diverifikasi utk separuh skenario.
2. **[KEPUTUSAN TERKUNCI — 2026-10-01] Generate traffic normal/benign secara eksplisit sebagai skenario tersendiri**, bukan hanya "sisa" dari idle time. UNSW-NB15 asli punya profil normal traffic terstruktur (browsing, DNS query wajar, file transfer legit). Tanpa ini, base rate class `normal` di dataset akan terlalu sintetik/tipis — rawan classifier overfit ke pola "diam = normal". Implementasi: script terjadwal (cron) di client-1/client-2/win-client — browsing/`curl` ke srv-web (halaman legit, bukan exploit), query DNS random ke `*.lab.local`, transfer file kecil legit ke srv-file — jalan beberapa jam per sesi, bukan cuma menit.
3. **[KEPUTUSAN TERKUNCI — 2026-10-01] Snapshot "golden" (v2 §1.4, dipakai utk win-client) diterapkan ke semua 8 VM**, bukan cuma win-client — reproducibility check v2 §4.5 ("hash pcap run1 = run2") jadi syarat tiap skenario, bukan eksklusif Windows phase. `VBoxManage snapshot "<vm>" take "golden"` setelah tiap VM mencapai state tervalidasi (network+tooling beres, pre-first-attack), restore sebelum tiap run skenario. **Status: SELESAI — 8/8 VM punya golden snapshot.** Snapshot 6 VM (router-opnsense, srv-web, srv-file, client-1, client-2, sensor) **diambil ulang 2026-10-06** setelah dua perbaikan: (a) NIC `NatNetwork-temp` yang masih menempel dilepas dari srv-web/srv-file/client-1/client-2 (nic2) dan sensor (nic5) — isolasi sebelumnya bocor; (b) `rtcuseutc on` di router (snapshot lama menyimpan `off` → jam maju 7 jam saat restore). attacker & win-client tidak berubah (NIC NAT sudah bersih, jam sudah benar). Blocker reproducibility v2 §4.5 (hash pcap run1 = run2) kini bisa mulai dibangun di atas baseline yang konsisten untuk seluruh 8 VM.
4. **`GroupShuffleSplit` berbasis `scenario_id`** (v2 §4.4) sudah tepat mencegah leakage — pertahankan, tapi tambahkan juga split berbasis **rentang waktu** (train = run awal, test = run ulang setelah restore snapshot) untuk menguji generalisasi model ke instance serangan yang sama tapi timing berbeda.
5. **Label `attack_cat` granularitas MITRE ATT&CK** — v2 sudah mapping tiap S-xx ke technique ID (T1021.004, T1003.001, dst). Simpan technique ID sebagai kolom terpisah di `dataset/schema.md` (saat ini schema hanya punya `attack_cat` generik), supaya dataset bisa dipakai utk evaluasi multi-granularitas (family-level vs technique-level).
6. **S-07 (LSASS dump + PtH)** — v2 sudah benar mengganti Mimikatz dengan `secretsdump.py`/`pypykatz` demi keamanan lab; pastikan keputusan ini dicatat di `docs/threat-references.md` sbg justifikasi metodologis saat penelitian ditulis (reviewer/pembimbing kemungkinan menanyakan kenapa bukan Mimikatz asli).
7. **Threat-to-validity yang perlu ditulis eksplisit di laporan akhir:** (a) skala lab kecil (8 VM) vs jaringan produksi — generalisasi terbatas; (b) attacker tunggal dari 1 titik (10.10.30.10) — tidak merepresentasikan multi-vector/distributed attacker; (c) tidak ada background noise dari user lain (kecuali direkayasa via poin #2 di atas).
8. **Dataset imbalance (v2 §4.4 sudah antisipasi via SMOTE + class_weight)** — tambahkan laporan distribusi kelas sebelum/sesudah SMOTE di `dataset/schema.md` atau notebook, karena reviewer akademik biasanya minta bukti bahwa oversampling tidak dilakukan di test set (v2 sudah benar secara kode — tinggal didokumentasikan sbg bagian dari metodologi, bukan hanya inline comment).
9. **[KEPUTUSAN TERKUNCI — 2026-10-01] Eksekusi skenario time-disjoint (non-overlap)** — normal-traffic generator dan tiap skenario attack dijalankan di window waktu terpisah, tidak pernah bersamaan; antar-skenario juga terpisah, bukan nyambung langsung. Ini basis labeling berbasis `[start_ts, end_ts]` per `scenario_id`. Syarat implementasi:
   - **Buffer gap 2–5 menit idle** antar run — mencegah residual koneksi/retransmit dari skenario sebelumnya bocor ke window berikutnya.
   - **Catat start/end timestamp presisi** (`date -u`) tiap run di level host — jadi source of truth kolom label, bukan estimasi "kira-kira jam segini".
   - **Clock sync lintas-VM wajib divalidasi** — lab isolated, tidak ada NTP eksternal. Rekomendasi: jalankan NTP server lokal di OPNsense (FreeBSD `ntpd` built-in), semua VM (termasuk sensor) sync ke situ via gateway segmen masing-masing. Tanpa ini, timestamp pcap di sensor bisa drift dari window yang dicatat di host → mislabel. **Status: SELESAI 2026-10-05** — NTP server lokal jalan di OPNsense (local clock fallback, stratum 10). Seluruh **7 VM client** (srv-web, srv-file, client-1, client-2, attacker, sensor, **win-client**) sudah dikonfirmasi synced ke OPNsense. win-client butuh fix tambahan (`W32Time` Windows, bukan `systemd-timesyncd`) — lihat `phase4-windows-client.md` §5 dan deviation log #17. **Koreksi 2026-10-06:** catatan sebelumnya di poin ini — bahwa waktu absolut lab sengaja tidak sama dengan waktu dunia nyata — **salah dan sudah dicabut**. Selisih ~7 jam yang dulu teramati adalah bug konfigurasi VirtualBox: VM `router-opnsense` memakai `rtcuseutc=off`, sehingga jam WIB host (UTC+7) dibaca OPNsense sebagai UTC, lalu jam yang maju 7 jam itu disebarkan ke VM lain lewat NTP. Dibetulkan 2026-10-06 dengan `VBoxManage modifyvm "router-opnsense" --rtcuseutc on` (lihat `phase2-opnsense-setup.md` §11). **Jam lab sekarang = UTC asli.** Verifikasi 2026-10-06: jam 8 VM dicek ulang dan semuanya cocok dengan UTC host (selisih hanya hitungan detik).
   - Masuk sbg item wajib baru di checklist Fase 6 (lihat §4 baris 6).
10. **[KEPUTUSAN TERKUNCI — 2026-10-02] Tranalyzer2 digantikan Argus** sebagai extraction layer offline (berjalan bareng Zeek, bukan live). UNSW-NB15 asli (Moustafa & Slay, 2015) memakai Argus+Bro-IDS sebagai pipeline capture-nya, bukan Tranalyzer2 — jadi Argus justru lebih setia ke metodologi dataset acuan dibanding pilihan Tranalyzer2 di v2. Argus aktif maintained (`github.com/openargus/clients`) dan terpaket resmi di Debian 13 (`argus-server`/`argus-client` 2:5.0.2-3), sementara Tranalyzer2 sudah tidak maintained (DNS `tranalyzer.com` mati, `tranalyzer.org` timeout). Implementasi: arsitektur **pcap-first** — tcpdump sebagai satu-satunya capture layer live, Zeek+Argus memproses pcap yang sama secara offline, Suricata tetap live af-packet khusus IDS alerting. Detail lengkap (49-kolom feature mapping, known issues) di `phase5-sensor.md` §7.

## 6. Dasar Keputusan (Rationale per Rekomendasi §5)

| # | Dasar | Konsekuensi jika diabaikan |
|---|---|---|
| 1 | Prinsip **symmetry of validation**: klaim "lab terisolasi" adalah properti dataset secara keseluruhan, bukan per-fase. v2 §4.5 ditulis khusus utk integrasi Windows (fokus dokumen v2), sehingga Linux phase tampak "dianggap sudah tervalidasi" — padahal belum ada checklist tertulis utk itu di sumber manapun yang tersedia. | Skenario S-01/02/03/04/08/09/11/12 (8 dari 12) berjalan tanpa bukti isolasi terverifikasi → temuan bisa dipertanyakan validitasnya saat sidang/review, karena tidak bisa dibuktikan traffic murni internal (tidak bocor ke NAT/internet). |
| 2 | Prinsip dasar **supervised learning**: kualitas kelas `normal` menentukan decision boundary classifier. UNSW-NB15 asli (Moustafa & Slay, 2015) secara eksplisit membangkitkan traffic normal terstruktur (bukan idle) via IXIA PerfectStorm — ini bagian dari desain dataset, bukan efek samping. Traffic "idle default" (ARP, NTP, DNS OPNsense-Unbound sendiri) punya profil statistik sangat sempit dan tidak representatif pengguna nyata. | Classifier belajar heuristik trivial ("ada traffic non-trivial = attack") yang tidak generalize ke deployment nyata; akurasi tinggi di dataset sendiri tapi tidak bermakna scientifically (dataset artifact, bukan sinyal attack yang sebenarnya dipelajari). |
| 3 | Prinsip **reproducibility dalam eksperimen** (bukan spesifik ML) — kondisi awal tiap run harus terkontrol/identik selain variabel yang sengaja diuji (skenario serangan). VM Linux sama rentannya drift antar-run seperti Windows: apt cache, systemd journal, `~/.ssh/known_hosts`, sisa proses/PID, ARP/neighbor cache — semua ini bisa menyisipkan variasi traffic non-skenario. v2 hanya menyoroti win-client karena itu fokus dokumen, bukan karena Linux kebal drift. | Jika hasil run 1 vs run 2 berbeda tanpa VM displit ke state awal yang sama, tidak bisa dibedakan apakah perbedaan itu berasal dari skenario serangan atau dari residu state VM sebelumnya — mengaburkan sebab-akibat (confounding). |
| 4 | Perbedaan antara **internal validity** dan **external validity** dalam evaluasi ML. `GroupShuffleSplit` per `scenario_id` mencegah model "menghafal" flow spesifik dari skenario yang sama muncul di train & test (internal validity — kebocoran within-run). Tapi ini tidak menguji apakah model general ke *instance baru* dari teknik yang sama pada waktu berbeda (external validity — real-world: SSH brute force besok jam berapa pun harus tetap terdeteksi, bukan cuma pola jam capture tertentu). Time-based split adalah cara standar menguji ini di literatur network intrusion detection. | Model bisa overclaim performa: baik di held-out scenario tapi gagal saat attack instance sama muncul di waktu/kondisi jaringan berbeda — gap ini baru ketahuan setelah deployment, bukan saat evaluasi. |
| 5 | v2 Instruksi 2 sendiri **sudah melakukan** mapping tiap skenario ke MITRE ATT&CK technique ID (T1021.006, T1003.001, T1550.002, T1021.004, dst) sebagai justifikasi akademik — tapi `dataset/schema.md` saat ini cuma punya kolom `attack_cat` bergaya UNSW-NB15 (9 kategori kasar). Kerja mapping yang sudah dilakukan v2 tidak ikut terbawa ke artefak dataset akhir. | Kontribusi granularitas yang sudah dirancang di blueprint (dan bisa jadi nilai tambah dibanding UNSW-NB15 original yang cuma family-level) hilang begitu saja di tahap implementasi — reviewer tidak bisa melihat/reproduce evaluasi technique-level meski sudah direncanakan. |
| 6 | Norma **metodologi riset keamanan**: penggantian tool ofensif riil (Mimikatz) dengan tool riset/forensik (secretsdump.py, pypykatz) adalah keputusan yang benar secara keamanan lab, tapi merupakan **deviasi dari TTP asli** yang direferensikan (CISA AA24-109A, dsb.) — deviasi metodologis semacam ini standar akademiknya harus dijustifikasi tertulis, bukan diasumsikan self-evident, karena mempengaruhi seberapa representatif traffic S-07 terhadap serangan LSASS-dump dunia nyata. | Pertanyaan sidang/reviewer "kenapa bukan Mimikatz" tidak punya jawaban tercatat; juga tidak ada catatan apakah traffic signature secretsdump.py cukup mirip dengan Mimikatz asli utk klaim S-07 tetap valid mewakili teknik T1003.001. |
| 7 | Konvensi baku **paper/tesis empiris bidang keamanan siber**: bagian "Limitations"/"Threats to Validity" adalah ekspektasi standar (bukan opsional) — absennya bagian ini sendiri adalah red flag bagi reviewer, terlepas dari seberapa bagus hasil eksperimen. Tiga poin (skala lab kecil, single-vector attacker, tidak ada background noise organik) adalah keterbatasan **struktural** dari desain lab ini yang tidak bisa dihilangkan, hanya bisa diakui dan dibatasi klaimnya. | Klaim generalisasi dataset/model bisa dianggap overclaiming tanpa pengakuan keterbatasan desain — melemahkan kredibilitas metodologis di mata penguji. |
| 8 | Best-practice ML pipeline utk imbalanced data: **kode v2 sudah benar** (SMOTE di-fit hanya pada train set, `MinMaxScaler` juga fit-only-train) — tapi kesalahan SMOTE-sebelum-split adalah salah satu **critical flaw paling sering ditemukan reviewer** pada paper NIDS berbasis ML (data leakage via oversampling). | 9 | Ground-truth labeling di dataset gaya UNSW-NB15 bersifat **window-based**: tiap flow dilabel berdasarkan apakah timestamp-nya jatuh di `[start_ts, end_ts]` suatu `scenario_id`. Kalau normal-traffic generator dan attack scenario overlap (atau antar-attack overlap), batas label jadi ambigu — flow di zona overlap tidak bisa dipastikan `attack_cat`-nya. Ini juga langsung berimplikasi ke rationale #3 (reproducibility) — tanpa clock sync yang valid, timestamp capture di sensor bisa tidak match sama window yang dicatat di host. | Flow ambigu di boundary skenario mencemari baik kelas `normal` maupun `attack_cat` tertentu; kalau clock antar-VM drift tanpa terdeteksi, seluruh proses assignment label pasca-capture jadi tidak reliable — bisa butuh re-capture total kalau ketauan belakangan. |
| 10 | Kesetiaan metodologis terhadap dataset acuan: UNSW-NB15 asli dibangun dengan Argus+Bro-IDS (lihat §7 tabel literatur poin 2), bukan Tranalyzer2 — jadi mengganti Tranalyzer2 dengan Argus bukan cuma soal tool mana yang masih maintained, tapi membuat pipeline ekstraksi fitur lebih dekat ke metodologi dataset yang jadi baseline riset ini. | Kalau tetap pakai Tranalyzer2 (sudah tidak maintained sejak ~2022, domain resminya mati per re-check 2026-10-02), risiko pipeline capture gagal total di tengah jalan tanpa upstream fix — dan secara metodologis tetap menyimpang dari tool asli UNSW-NB15 meski sempat jalan. |
