## 5. Research Recommendations

1. **The Phase 6 validation checklist in v2 §4.5 only covers the Windows phase.** Build a parallel version for the Linux phase (client-1/2/attacker↔internet isolation, `*.lab.local` DNS resolution, UTC time sync) before executing scenarios S-01/02/03/04/08/09/11/12 — without it, the "isolated lab" claim cannot be verified for half the scenarios.
2. **[LOCKED DECISION — 2026-10-01] Explicitly generate normal/benign traffic as its own scenario**, not just idle-time "leftovers." The original UNSW-NB15 has a structured normal-traffic profile (browsing, ordinary DNS queries, legitimate file transfer). Without this, the `normal` class base rate in the dataset will be too synthetic/thin — the classifier risks overfitting to "silence = normal." Implementation: scheduled scripts (cron) on client-1/client-2/win-client — browsing/`curl` against srv-web (legitimate pages, not exploits), random DNS queries against `*.lab.local`, small legitimate file transfers to srv-file — run for hours per session, not just minutes.
3. **[LOCKED DECISION — 2026-10-01] "Golden" snapshots (v2 §1.4, used for win-client) applied to all 8 VMs**, not just win-client — the reproducibility check in v2 §4.5 ("pcap hash run1 = run2") is now a requirement for every scenario, not exclusive to the Windows phase. `VBoxManage snapshot "<vm>" take "golden"` once each VM reaches a validated state (network+tooling done, pre-first-attack), restored before every scenario run. **Status: DONE 2026-10-05 — 8/8 VMs now have a golden snapshot**, confirmed via `VBoxManage snapshot "<vm>" list` for every VM:

The v2 §4.5 reproducibility requirement (pcap hash run1 = run2) can now be built on a consistent baseline across all 8 VMs.
4. **`GroupShuffleSplit` on `scenario_id`** (v2 §4.4) correctly prevents leakage — keep it, but also add a **time-based** split (train = initial run, test = re-run after snapshot restore) to test the model's generalization to new instances of the same attack at different timings.
5. **`attack_cat` label granularity vs MITRE ATT&CK** — v2 already maps each S-xx to a technique ID (T1021.004, T1003.001, etc.). Store the technique ID as a separate column in `dataset/schema.md` (currently only a generic `attack_cat` field), so the dataset can support multi-granularity evaluation (family-level vs technique-level).
6. **S-07 (LSASS dump + PtH)** — v2 correctly replaces Mimikatz with `secretsdump.py`/`pypykatz` for lab safety; make sure this decision is recorded in `docs/threat-references.md` as a methodological justification when the research is written up (a reviewer/advisor will likely ask why not real Mimikatz).
7. **Threats-to-validity to state explicitly in the final report:** (a) small lab scale (8 VMs) vs. a production network — limited generalizability; (b) a single attacker vantage point (10.10.30.10) — does not represent a multi-vector/distributed attacker; (c) no background noise from other users (unless engineered via point #2 above).
8. **Dataset imbalance (v2 §4.4 already anticipates this via SMOTE + class_weight)** — add a class-distribution report before/after SMOTE to `dataset/schema.md` or the notebook, since academic reviewers typically want evidence that oversampling was not applied to the test set (v2's code is already correct — it just needs to be documented as part of the methodology, not left as an inline comment).
9. **[LOCKED DECISION — 2026-10-01] Time-disjoint (non-overlapping) scenario execution** — the normal-traffic generator and every attack scenario run in separate time windows, never simultaneously; scenarios are also kept separate from each other, not run back-to-back with no gap. This is the basis for `[start_ts, end_ts]`-window labeling per `scenario_id`. Implementation requirements:
   - **2–5 minute idle buffer** between runs — prevents residual connections/retransmits from a prior scenario leaking into the next window.
   - **Record precise start/end timestamps** (`date -u`) for every run at the host level — this becomes the source of truth for the label column, not a rough "around that time" estimate.
   - **Cross-VM clock sync must be validated** — the lab is isolated, no external NTP access. Recommendation: run a local NTP server on OPNsense (FreeBSD's built-in `ntpd`), with every VM (including sensor) syncing to it via its segment's gateway. Without this, sensor pcap timestamps can drift from the window recorded at the host → mislabeling. **Status: DONE 2026-10-05** — local NTP server running on OPNsense (local clock fallback, stratum 10). All **7 client VMs** (srv-web, srv-file, client-1, client-2, attacker, sensor, **win-client**) are now confirmed synced to OPNsense. win-client needed an extra fix (Windows `W32Time`, not `systemd-timesyncd`) — see `phase4-windows-client.md` §5 and deviation log #17. **Important note:** the lab's absolute time does NOT match real-world time (OPNsense's stratum-10 fallback has an arbitrary offset from real-world time) — this is by design; what matters is relative consistency across VMs, not matching real UTC/local time.
   - Added as a new mandatory item to the Phase 6 checklist (see §4 row 6).
10. **[LOCKED DECISION — 2026-10-02] Tranalyzer2 replaced by Argus** as the offline extraction layer (run alongside Zeek, not live). The original UNSW-NB15 (Moustafa & Slay, 2015) used Argus+Bro-IDS as its capture pipeline, not Tranalyzer2 — so Argus is actually more faithful to the reference dataset's methodology than v2's original Tranalyzer2 choice. Argus is actively maintained (`github.com/openargus/clients`) and officially packaged in Debian 13 (`argus-server`/`argus-client` 2:5.0.2-3), while Tranalyzer2 is no longer maintained (`tranalyzer.com` DNS dead, `tranalyzer.org` times out). Implementation: **pcap-first** architecture — tcpdump as the sole live capture layer, Zeek+Argus both processing the same pcap offline, Suricata staying on live af-packet for IDS alerting only. Full detail (49-column feature mapping, known issues) in `phase5-sensor.md` §7.

## 6. Decision Rationale (per Recommendation in §5)

| # | Rationale | Consequence if ignored |
|---|---|---|
| 1 | **Symmetry-of-validation** principle: the "isolated lab" claim is a property of the dataset as a whole, not per-phase. v2 §4.5 was written specifically for the Windows integration (that document's focus), so the Linux phase appears "assumed already validated" — even though no written checklist for it exists in any available source. | Scenarios S-01/02/03/04/08/09/11/12 (8 of 12) run without verified proof of isolation → findings can be questioned for validity during defense/review, since pure internal traffic (no leak to NAT/internet) cannot be demonstrated. |
| 2 | Basic **supervised learning** principle: the quality of the `normal` class determines the classifier's decision boundary. The original UNSW-NB15 (Moustafa & Slay, 2015) explicitly generated structured normal traffic (not idle) via IXIA PerfectStorm — this is part of the dataset's design, not a side effect. "Default idle" traffic (ARP, NTP, OPNsense-Unbound's own DNS) has a very narrow statistical profile and is not representative of real users. | The classifier learns a trivial heuristic ("any non-trivial traffic = attack") that does not generalize to real deployment; high accuracy on the dataset itself but not scientifically meaningful (a dataset artifact, not the actual attack signal being learned). |
| 3 | **Experimental reproducibility** principle (not ML-specific) — the starting condition of every run must be controlled/identical apart from the deliberately varied variable (the attack scenario). Linux VMs are just as prone to inter-run drift as Windows: apt cache, systemd journal, `~/.ssh/known_hosts`, leftover processes/PIDs, ARP/neighbor cache — all of these can inject non-scenario traffic variation. v2 only highlighted win-client because that was the document's focus, not because Linux is immune to drift. | If run 1 vs. run 2 results differ without the VM being reset to the same starting state, it becomes impossible to tell whether the difference came from the attack scenario or from residual VM state — confounding cause and effect. |
| 4 | The distinction between **internal validity** and **external validity** in ML evaluation. `GroupShuffleSplit` on `scenario_id` prevents the model from "memorizing" specific flows from the same scenario appearing in both train and test (internal validity — within-run leakage). But it does not test whether the model generalizes to *new instances* of the same technique at a different time (external validity — real-world: SSH brute force must still be detected whenever it occurs, not just match a specific capture-time pattern). Time-based splitting is the standard way to test this in the network intrusion detection literature. | The model can overclaim performance: good on a held-out scenario but failing when the same attack instance occurs under different timing/network conditions — a gap only discovered after deployment, not during evaluation. |
| 5 | v2 Instruction 2 **already performs** the mapping of each scenario to a MITRE ATT&CK technique ID (T1021.006, T1003.001, T1550.002, T1021.004, etc.) as academic justification — but `dataset/schema.md` currently only has a UNSW-NB15-style `attack_cat` column (9 coarse categories). The mapping work v2 already did never carries through to the final dataset artifact. | The granularity contribution already designed into the blueprint (and a potential value-add over the original UNSW-NB15, which is family-level only) is simply lost at implementation time — a reviewer cannot see/reproduce a technique-level evaluation even though it was planned. |
| 6 | Norm of **security research methodology**: replacing a real offensive tool (Mimikatz) with a research/forensic tool (secretsdump.py, pypykatz) is the right call for lab safety, but it is a **deviation from the referenced original TTP** (CISA AA24-109A, etc.) — this kind of methodological deviation is academically expected to be justified in writing, not assumed self-evident, since it affects how representative the S-07 traffic is of a real-world LSASS-dump attack. | A defense/review question of "why not real Mimikatz" has no recorded answer; nor is there any note on whether secretsdump.py's traffic signature is close enough to real Mimikatz for the S-07 claim to still validly represent technique T1003.001. |
| 7 | Standard convention of **empirical cybersecurity papers/theses**: a "Limitations"/"Threats to Validity" section is a standard expectation (not optional) — its absence is itself a red flag for reviewers, regardless of how good the experimental results are. The three points (small lab scale, single-vector attacker, no organic background noise) are **structural** limitations of this lab's design that cannot be removed, only acknowledged and scoped in the claims made. | Generalization claims about the dataset/model can be seen as overclaiming without acknowledging design limitations — weakening methodological credibility in front of examiners. |
| 8 | Best-practice ML pipeline for imbalanced data: **the v2 code is already correct** (SMOTE fit only on the train set, `MinMaxScaler` also fit-only-train) — but SMOTE-before-split is one of the **most commonly found critical flaws** by reviewers in ML-based NIDS papers (data leakage via oversampling). An inline code comment is not sufficient as audit evidence; a separate artifact is needed (a table/plot of the class distribution pre/post-SMOTE, split by train/test) that can be checked independently of the code. | A skeptical reviewer (correctly so, given how prevalent this mistake is in the literature) has no quick way to verify the implementation is correct without re-reading the entire codebase — slowing/complicating the review process even though the implementation is already right. |
| 9 | Ground-truth labeling in UNSW-NB15-style datasets is **window-based**: every flow is labeled according to whether its timestamp falls within a given `scenario_id`'s `[start_ts, end_ts]`. If the normal-traffic generator and an attack scenario overlap (or two attack scenarios overlap), the label boundary becomes ambiguous — flows in the overlap zone cannot be confidently assigned an `attack_cat`. This also directly feeds into rationale #3 (reproducibility) — without validated clock sync, sensor capture timestamps may not match the window recorded at the host. | Ambiguous flows at scenario boundaries contaminate both the `normal` class and specific `attack_cat` labels; if inter-VM clock drift goes undetected, the entire post-capture labeling process becomes unreliable — potentially requiring a full re-capture once discovered. |
| 10 | Methodological fidelity to the reference dataset: the original UNSW-NB15 was built with Argus+Bro-IDS (see §7 literature table point 2), not Tranalyzer2 — so replacing Tranalyzer2 with Argus is not just about which tool is still maintained, it brings the feature-extraction pipeline closer to the methodology of the dataset this research is baselined on. | Sticking with Tranalyzer2 (unmaintained since ~2022, its official domains dead per the 2026-10-02 re-check) risks the capture pipeline failing outright mid-project with no upstream fix — and remains a methodological deviation from UNSW-NB15's actual tooling even while it still works. |
